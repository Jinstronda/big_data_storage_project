Main idea

The checkout receipt is the natural unit of the database. Branch, customer, payment, item, totals, and rating stay together because the store reads them together.

The dataset is small enough to defend, but real enough to model

Why not split into many collections

The assignment asks for business reads. Most reads start from the receipt, so extra collections would add joins without adding much value.

Tradeoff

Branch and product names repeat. That is acceptable here. If this became a production stock system, product catalogue and inventory collections would make sense.

Validation blocks the mistakes that would break the numbers

Indexes were added only where a query needed them

sale_datetime
date range reads

branch.code plus sale_datetime
branch and month query

items.product_line plus total
high value category query

payment.method plus date
payment review

rating plus total
low rating follow up

The rule I used

No random indexes. Each index maps to one query or aggregation used in the report. The dataset is only 1000 receipts, so the gain is small now, but the same pattern matters when the table grows.

How I would say it

This is not a speed demo with millions of rows. It is a modelling demo. The index plan proves that the queries were designed with read patterns in mind.

The tradeoff is repeated text, not query complexity
